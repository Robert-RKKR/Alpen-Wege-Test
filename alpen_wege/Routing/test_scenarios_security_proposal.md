## 1. Your main question: test per model, per app, or something else?

**Short answer: neither. Test per *resource key* (and per *code path*), generated by a loop.**

Why. In this project permission is not decided by the model or by the app. It is decided by one row in `profile_access_policy`:

`user_group + resource_key + action  ->  scope (own / public / all)`

and the route only says `resource_access("poi", "read")`. So the real unit is the **resource key**. Look at how it differs from models and apps:

| Idea | Why it does not fit |
|---|---|
| Per app (explorer, compendium...) | One app holds many keys with different rules (compendium: editor may create/update/delete, but `ref` is read-only for editor). |
| Per model (table) | `ref` is **19 tables with one key** (`ref.py` builds 19 routers from one factory). Testing 19 times the same rule is waste. But 7 compendium route files are *copy-pasted*, so a bug can hide in only one of them. |
| **Per resource key** | Matches exactly what the policy table controls. 16 keys x 4 groups x 4 actions = 256 cells. |

So the design is **three layers**. Each layer is a loop, not hand-written tests:

| Layer | Question it answers | Loop over | Size |
|---|---|---|---|
| L0 Classification (new in v2) | "Does every route have exactly one protection class?" | every route + WebSocket route | 1 test, grows by itself |
| L1 Matrix | "Can group G do action A on key K — yes or no?" | group x key x action | 256 cells (144 testable today with 9 keys, see below) |
| L2 Scope | "If yes, on *which rows* — own, public or all?" | every route **file** (copy-paste risk) x 3 scope cases | ~8 files x ~4 cases |
| L3 Relations | "Does a link between two models leak or bypass a permission?" | every parent -> child relation | small, handwritten, see section 5 |
| L4 Owner-gated (new in v2) | "Can user B reach user A's jobs or sockets?" | jobs REST, WebSocket, job-start endpoints | small, see section 5b |

Plus one **sweep** that needs no list at all: read `/openapi.json`, call every endpoint without a token, expect 401. This catches a forgotten `Depends(...)` on any new route in any app.

**Today these keys have routes:** `gear`, `track` (explorer), `poi`, `country`, `region`, `card`, `post`, `poi_region` (compendium) and `ref` (19 tables) = **9 keys**. Keys `trip, journey, route, segment, photo, gpx, achievement` have policies in the seed but **no routes yet**. Matrix tests should skip a key automatically while it has no route, and start running the day the route appears (so you cannot forget).

## 1b. New in v2: the management APIs use two other kinds of protection

When I read `app/management/**` I found that the new endpoints do **not** use the policy table at all. There are now **three kinds of protection** in the project, and each needs its own kind of test:

| Kind | How the code does it | Used by | Test layer |
|---|---|---|---|
| A. Policy key | `resource_access("poi", "update")` -> reads `profile_access_policy` | gear, track, compendium, ref | L1 matrix + L2 scope (section 4) |
| B. Role gate | `require_groups("administrator")` -> hard-coded in the route, **not** changeable by an admin through policies | users admin, resource-types, access-policies, `/management/event-log`, `/management/settings`, `/management/jobs`, `/management/broadcast`, `/management/celery` | L0 + new section 5b |
| C. Owner gate | any active user, but the code compares `job.user_id == me` (and answers 404 for "not yours") | `/jobs`, `/jobs/{id}`, `/ws/ticket`, WebSocket `/ws`, `/ws/jobs/{id}` | L4 + new section 5b |

A forgotten gate is the most likely security bug when new routes are added quickly. So v2 adds a **route classification contract (L0)**, which needs no manual list per route in the test body:

1. Read the app's route table (OpenAPI **plus** the two WebSocket routes, which OpenAPI does not show).
2. Every route must be placed in **exactly one** class in one small file `route_classes.py`: `public`, `any_user`, `policy_key`, `admin_only`, `owner_only`.
3. A route that is in no class **fails the test**. So the day someone adds a new endpoint, the test forces a decision.
4. For each class there is a generic check: `public` -> works without token; everything else -> 401 without token; `admin_only` -> 403 for editor/viewer/guest, 2xx for admin; `owner_only` -> user B gets the same 404 as for a missing id; `policy_key` -> goes to the matrix (L1).

## 2. Test setup (needed by everything)

Expected matrix = the "contract". Write it **once** in the test code (copy of the table below), and also compare it with the live `GET /auth/access-policies`. If someone changes the seed or a policy by accident, one test fails.

| Group | explorer / asset / achievement keys | compendium keys | `ref` |
|---|---|---|---|
| administrator | create / read / update / delete = all | all four = all | all four = all |
| editor | create own, read **public**, update own, delete own | create own, read **all**, update own, delete own | read all |
| viewer | same as editor | read all only | read all |
| guest | read **public** only | read all | read all |

Test users (created fresh each run by `register`, then promoted by the admin API — this is also your scenario AUTHZ-01):

- `admin` (the seeded one, only used to promote and to read policies)
- `editor_a`, `editor_b`, `viewer_a`, `viewer_b`, `guest_a`

Two users per group are needed so we can test "my row vs somebody else's row" inside the same group.

Short token lifetime: `JWT_EXPIRE_MINUTES` is **999** now (about 16.6 hours), and rotation happens at half of it. Token-rotation tests need an environment override (for example 2 minutes), otherwise they cannot run.

### 4.2 L1 — Permission matrix (your "5 models x all actions")

Instead of 5 hand-picked models, use **all routed keys** (9 today, including `track`). For each key we need one *representative request per action*:

| Action | Request used |
|---|---|
| create | `POST /{resource}` with a minimal valid body (one fixture per key) |
| read | `GET /{resource}` and `GET /{resource}/{id}` |
| update | `PATCH /{resource}/{id}` |
| delete | `DELETE /{resource}/{id}` |
| create (CSV) | `POST /{resource}/upload-csv` (uses the *create* permission) |

Rules for the check:

- Expected **allowed** -> status 2xx.
- Expected **denied by policy** (no row for that group+action) -> **403**.
- Expected **denied by scope** (object exists but belongs to somebody else) -> **404** (the code hides existence on purpose).
- Missing or invalid token -> 401.
- Order: a forbidden user who sends an *invalid body* must get 403, not 422 (otherwise we leak the shape of the schema).

For `ref` run the full matrix on 2 representative tables (one "base", one "with factor") and the 401 sweep on all 19.

Note: `track` create is a **multipart file upload** (`POST /tracks` with a `.gpx` file) and answers **202** (not 201) because processing runs in a job; its fixture is a small valid GPX. `track` delete is a **soft delete** (archive) and has two extra routes (`restore`, `reprocess`) that count as *update*.

Result: 9 keys x 4 groups x ~5 requests = **about 180 cases**, generated by `pytest.mark.parametrize`, runs in seconds. Each case is one line in a table, so the failure message reads like "editor / poi / delete / expected 404 got 200".

## 5. L3 — Relations between models ("one model can be related to many")

Because permission is checked **only for the key of the endpoint**, any other model that travels *inside* the answer, or is *linked by id*, is a potential bypass. Today it is low risk (compendium and ref are readable by everybody), but it becomes real when explorer routes arrive (a public track that links a private photo, gear, gpx). So write the tests now, with the rule fixed in advance.

**Proposed rule R:** *an embedded or linked object is only shown or accepted if the caller could read it directly.*

| ID | Scenario | Expected |
|---|---|---|
| REL-01 | **Embedded child.** `PoiRead` embeds `compendium_type` and `main_region`. For every nested object in every Read schema: user with no read on the child key / row | child is hidden (id only or null), never full data |
| REL-02 | **Linking by id.** Create/patch parent with a child id the caller cannot read (someone else's private row) | 404 or 422, never 201 |
| REL-03 | **Delete parent that has children of other users** (editor_a deletes own POI, editor_b owns a card pointing to it) | 409 with clear message, or a defined cascade — never silent loss of `editor_b`'s card |
| REL-04 | **Link tables** (`poi_region`, later `track_poi`, `track_photo`): user may link only things he may read, and only on a parent he may update | otherwise 403 / 404 |
| REL-05 | **Planned `?expand=`**: the expanded child follows the child's own read policy, not the parent's | same as REL-01 (write this test together with the expand feature) |
| REL-06 | **Sub-resource of a forbidden parent** | 404, same as parent |

## 5b. New APIs: management, logs, jobs, WebSocket, upload (new in v2)

Plain words first, because some names are new: the **event log** is the audit trail ("who changed what, when"); a **job** is one background task of a user (for example processing an uploaded GPX file) that you can follow; the **WebSocket** is a permanent connection that pushes job progress to the browser; **Celery** is the worker system that runs the jobs; **settings** are values an admin can change while the app runs.

**Extra test setup for this section**

- The tests need the **real stack**: API, Postgres, Redis and a running Celery worker (the management app is not yet deployed on your host, see D1 and D11).
- A WebSocket client in the tests (the Python package `websockets`).
- To avoid waiting an hour, tests shorten timers **through the settings API itself**: `ws.ticket_ttl_s` to 5 seconds, `ws.max_lifetime_s` to 60 seconds. A fixture puts the original values back after each test.
- Test users are the same as in section 2 (`admin`, `editor_a/b`, `viewer_a/b`, `guest_a`).
